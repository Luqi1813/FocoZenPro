### Fase 2 — Otimizações de Performance e Segurança (Risco: BAIXO, Tempo: 1-2h)

**Objetivo:** Reduzir RAM, melhorar segurança, sem mudar arquitetura.

#### 2.1 — Remover duplicações de dados (~50 linhas economizadas)

`renderer.js` duplica dados que já existem em `constants.js`:
- `soundsConfig` (linhas ~36-48) → usar `window.FocoZenConstants.soundsConfig`
- `storageKeys` (linhas ~14-34) → usar `window.FocoZenStorage.storageKeys`
- `quotes` e `successQuotes` (linhas ~62-75) → usar `window.FocoZenConstants.quotes`
- `motivationalRestartMessages` → usar `window.FocoZenConstants.motivationalRestartMessages`
- `POMODORO_MINUTES`, `SHORT_BREAK_MINUTES`, `LONG_BREAK_MINUTES` → usar `window.FocoZenConstants`
- `defaultCategories` → usar `window.FocoZenConstants.defaultCategories`
- `soundCategories` → usar `window.FocoZenConstants.soundCategories`
- `soundThemes` → usar `window.FocoZenConstants.soundThemes`

**Como:** Substituir referências locais por `constantsService.*`. O fallback `??` já existe — basta remover as declarações duplicadas.

**Economia:** ~40 linhas + ~10KB de dados duplicados em memória.

#### 2.2 — Aumentar limite de memória RAM

De `--max-old-space-size=256` para `--max-old-space-size=512` em `main.js`.
- 256MB é agressivo demais para um app com Chart.js + React + 7000 linhas de JS
- 512MB ainda é conservador mas evita GC thrashing

#### 2.3 — Sanitização de inputs (segurança)

Adicionar `escapeHtml()` antes de qualquer `innerHTML` com dados do usuário:
- Task names em `renderTasksList()` e `renderTasksSidebar()`
- Username em `updateSidebarProfile()`
- Assistant messages

**Gate:** `npm run test` ✅, smoke completo

### Fase 3 — Modularização Real do renderer.js (Risco: MÉDIO, Tempo: 3-4h)

**O Problema Real:** Variáveis `let` locais não são acessíveis de scripts externos. A única forma de dividir o arquivo é convertê-lo para **ES modules**.

#### Abordagem: ES Modules via `<script type="module">`

**Passo 1:** Criar `src/renderer/state.js` — todas as variáveis de estado exportadas:
```js
export let tasks = [];
export let currentTask = null;
export let timeLeft = 25 * 60;
// ... todas as ~40 variáveis
export function setTasks(v) { tasks = v; }
// ... setters para cada uma
```

**Passo 2:** Criar módulos por domínio que importam de `state.js`:
```
src/renderer/
  ├── state.js           (~100 linhas) — estado compartilhado
  ├── timer-engine.js    (~400 linhas) — timer logic
  ├── tasks-manager.js   (~500 linhas) — task CRUD
  ├── home-manager.js    (~350 linhas) — audio, category, free focus
  ├── modals.js          (~300 linhas) — wizard, newTask, transition, toast
  ├── categories.js      (~80 linhas)  — category editing
  ├── dashboard.js       (~600 linhas) — stats/goals data + charts
  ├── assistant.js       (~800 linhas) — assistant NLP + handlers
  ├── pip-sync.js        (~150 linhas) — PiP state sync
  ├── navigation.js      (~50 linhas)  — switchView, initNavigation
  └── runtime-exports.js (~200 linhas) — window.FocoZen*Runtime
```

**Passo 3:** Criar `src/renderer/index.js` — módulo principal que importa tudo:
```js
import * as state from './state.js';
import './timer-engine.js';
import './tasks-manager.js';
// ... etc
```

**Passo 4:** Mudar `index.html` de:
```html
<script src="renderer.js"></script>
```
Para:
```html
<script type="module" src="src/renderer/index.js"></script>
```

**Passo 5:** Deletar `renderer.js` raiz.

**Por que funciona:** ES modules suportam `import/export` nativamente no Electron (Chromium moderno). Cada módulo pode importar `state.js` e acessar/modificar as variáveis compartilhadas.

**Riscos mitigados:**
- Um módulo por vez, com smoke após cada um
- `npm run test` roda após cada módulo
- Branch preservada para rollback
- O section index existente serve como mapa de migração

**Resultado final:**
- `renderer.js` raiz → **deletado**
- 11 módulos de 50-800 linhas cada (média ~300)
- Estado centralizado em `state.js` (~100 linhas)
- Zero duplicação de dados
- Import/export explícito — fácil rastrear dependências
